# Publikacja bez GitHub Actions Artifacts

`build.yml` wywołuje ten sam workflow platformowy dla Windows i ARM64. Każdy job zachowuje konfigurację, kompilację i testy swojej platformy, pakuje wynik i weryfikuje architekturę oraz manifest. Potem **ten sam job** przesyła gotowe pliki do GitHub Release. Między zadaniami nie przechodzą żadne binaria; nie ma `download-artifact` ani Artifacts jako warunku publikacji.

Pull requesty wykonują identyczne testy z `contents: read`, bez publikacji. Zaufane push/dispatch uruchamiają dedykowane zadania `release-windows` i `release-arm64` z `contents: write`. Wywołany workflow dziedziczy zakres; standardowy job-scoped `GITHUB_TOKEN` jest udostępniany tylko krokowi publikacji jako GH_TOKEN. PAT ani dodatkowy sekret nie są potrzebne. `persist-credentials: false` ogranicza pozostawianie poświadczeń przez checkout.

Numer bazowy pochodzi z `VERSION`. Przykład tagu: `v0.1.0-preview.1.ci.40500000000.1`; zawsze prerelease. Run ID i attempt zapobiegają kolizjom, tag jest przypięty do konkretnego SHA. Równoległe platformy korzystają z tego samego tagu; publisher obsługuje wyścig tworzenia Release. Pliki pojawiają się po ukończeniu testów danej platformy. Release z jedną platformą jest częściowym wynikiem, nie deklaracją sukcesu drugiej.

Każde wydanie ma instrukcje Windows/RPi oraz wykaz oczekiwanych plików. Rzeczywiście przesłane nazwy, rozmiary i SHA256 znajdują się w `FILES-Windows-x64.json` / `FILES-RPi-aarch64.json` i osobnych manifestach sum. Rozdzielone nazwy nie kolidują między zadaniami. Paczki zawierają odpowiadające źródła, ale nie prompt użytkownika, archiwum referencyjne, ilustracje, .git, .env, tokeny, logi, cache, .obj/.o/.pdb ani narzędzia chmury. Runtime RPi ma jawną listę wymaganych skryptów; źródła zawierają tylko śledzone pliki produktu i niezbędną część przypiętego SDK.

Publisher odmawia nadpisania istniejących assetów i nie usuwa tagów, wydań ani wcześniejszych artefaktów. Ponowne uruchomienie całego workflow tworzy nowy tag attempt, zachowując wcześniejsze wyniki. Gdy próba zostanie przerwana podczas uploadu, należy uruchomić nową próbę zamiast kasować istniejące pliki. Ten preview pozostaje prywatny z uwagi na jawnie opisane nierozstrzygnięte noty licencyjne; workflow nie zmienia widoczności repozytorium.

Pomocnicze Artifacts są **domyślnie wyłączone**, niezależne od paczek. Opcjonalny `workflow_dispatch → upload_diagnostics` przesyła wyłącznie sanitizowane podsumowanie (platforma i status), z `retention-days: 1`. Błąd tej pomocniczej operacji nie unieważnia już przesłanych Releases ani testów. Pełne logi pozostają standardowymi logami przebiegu Actions, bez kopiowania ich do produktów.

Sprawdzenia: actionlint, testy tagów/allowlisty/wyścigu, kontrola braku operacji usuwania/nadpisywania, testy wykluczania wartości prywatnych, odczyt faktycznych ZIP/TAR i SHA256. Końcowym potwierdzeniem uprawnień jest utworzenie prerelease i weryfikacja rozmiarów/digestów przez GitHub API w rzeczywistym CI. Nie zmieniamy limitów storage, billing ani polityk organizacji. Jeżeli organizacja ogranicza token mimo deklaracji `contents: write`, publikacja zakończy się czytelnym błędem i wymaga korekty polityki przez właściciela.
